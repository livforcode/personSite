# 基于go的高并发房间状态同步系统服务-狼人杀版本

![](https://imgstroe-redblacktree.oss-accelerate.aliyuncs.com/img/20260324174915074.png)

## 场景

1. 狼人杀游戏中，多名玩家需要进行投票和发言，在实际场景中，需要满足高并发下的**状态同步**和**即时语音**
2. 由于涉及海外服务器，因此网络状态不稳定，需要支持**弱网，快速断线重连**
3. **分布式**容器化部署，支持动态扩展，全链路监控指标，如p99,**自动限流**熔断，防止雪崩

## 方案

### 语音流采用QUIC,状态快照 + 增量更新实现快速断线重连

QUIC相较于传统tcp在语音流传输中有着更强的优势。语音流要求低延迟，防止丢包以及应对网络抖动和快速重连，而传统tcp采用三次握手建立，且严格保证有序到达，导致若中间某个包丢失，其他包都得等待发送，且重建联系需要1个**RTT**。QUIC底层是基于**UDP**，在建立需要一个RTT但是重连可以数据随着握手信号一起发送，因此可达**0RTT**。不保证有序到达，因此在弱网情况下能够达到更高的传输效率，在语音中，网络不好只会出现**破音**而非**语音延迟**。
且UDP属于用户态下内容，后续可以进行更多控制，比如调整重传策略，做前向纠错等。

![](https://imgstroe-redblacktree.oss-accelerate.aliyuncs.com/img/20260325101042442.png)
弱网情况下，TCP与QUIC对语音传输效率比较

### Go原生的Actor模型支持高并发

在java中，多线程对于临界资源的竞争是通过加锁解决的，但是java本身线程在切换需要不断从用户态和核心态进行切换，因此所需要时间更多。
而go通过协程通过在用户态进行调度，相较于加锁，通过通道传输临界区资源，避免线程阻塞，保证始终处于流水线作业
java线程切换和最小线程分别为1~10 us，1MB，而go中，由于不涉及到用户态核心态切换，时间分别为0.1~0.5us，初始栈空间仅约 2KB。理论上在 **10000** 线程并发时java线程切换所耗时间5ms ~ 50ms，占据空间5GB，而此时go仅仅需要大约空间**10MB**，时间**0.5ms ~ 2.5ms**

![](https://imgstroe-redblacktree.oss-accelerate.aliyuncs.com/img/20260319045332827.png)

### 通过一致性哈希维护分布式,支持动态扩容，限流熔断

考虑扩展性，因此通过网关+n个后端节点实现更加合理，其中网关通过hash算法将请求分发给不同后端节点，但是这样不利于应对特殊情况以及扩展节点，比如某个后端挂了后，所有的映射关系都被打乱，需要重新计算，因此通过一致性哈希解决这个问题。

![](https://imgstroe-redblacktree.oss-accelerate.aliyuncs.com/img/20260325111618792.png)

这样的话，即使挂了后，只需将挂了后端节点上的任务搬到顺时针的下一个节点上。更优化一些的话，可以通过**快照+操作日志**的方法，即使后端节点丢失，能够快速恢复，而仅仅丢失几s内数据。

在这个基础上，因为网关控制任务分发，我们可以通过心跳包，后端节点的负载因子来进行动态控制流量，实现限流熔断，监控等。由于docker的存在，通过CI/CD流水线，我们可以很容易实现动态扩容，当网关发现所有后端节点承受负荷达到预定值，动态启动新一个后端容器镜像。

![](https://imgstroe-redblacktree.oss-accelerate.aliyuncs.com/img/20260325111605833.png)

## 系统框架

![](https://imgstroe-redblacktree.oss-accelerate.aliyuncs.com/img/20260325111544599.png)

在语音传输中，后端节点仅负责连接管理和音频包转发，，对客户端上传的音频数据进行零拷贝或最小处理的中继转发，不做解码、混音等计算密集操作。同时结合业务逻辑（如闭麦、活跃说话人）进行选择性分发而非简单广播。

redis 根据需要，可以后续扩展成redis群的形式，比如说哨兵，Cluster模式，但是在这个场景中，由于redis本身基于内存的高性能存储，不属于核心性能瓶颈
