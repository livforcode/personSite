# go高性能并发浅析
![](https://imgstroe-redblacktree.oss-accelerate.aliyuncs.com/img/20260319041854083.png)
在接触 Go 之前，我做小项目一般用 Python + Flask，很快就能跑起来；一旦项目稍微正规一点，就基本会转到 Java，用 Spring / Spring Boot 那一套。

Spring 生态确实很成熟：缓存有 Redis，微服务、分布式都有现成方案，整个开发流程非常“工业化”。但用久了会有一种奇怪的感觉——像是在操作一台很复杂但封装得很好的机器。DI、IoC 这些东西确实提高了效率，但也把很多底层细节藏起来了。很多时候你只是按套路写代码：定义接口、注入 Bean、写配置，更像是在“填空”，而不是在真正理解系统是怎么运转的。稳定是稳定，但总感觉少了点掌控感。

后来接触到 Go，第一感觉就是——简单、直接，没有那么重的框架，也没有那么多抽象。并发、调度这些能力语言里就给你了，用起来很自然。有点像当初学 C 的时候，一切都很“贴近底层”，没有被层层包住。像一些Kubernetes、Docker都是由他实现的，号称能轻松上“百万并发”，拳打Java，但是我有点好奇，同样是线程，他是怎么实现的优化。


## go,c++,java

Java 通过 JVM 和 JIT 编译，在运行时对热点代码进行优化，因此在长时间运行的服务中可以获得接近原生代码的性能，但代价是更高的内存占用和 GC 开销。
Go 作为静态编译语言，直接生成机器码，同时引入轻量级 GC，在开发效率和运行性能之间取得平衡。相比 C++，Go 通过简化语言特性（如去除继承和函数重载）降低了编译复杂度，但是是有种简化过头的感觉，特别是类没了，还有恐怖的函数返回嵌套函数 ( º﹃º )

## GMP模型

1. 在java中，线程最终是分配到系统线程中进行执行的，每一次的线程调用，都会涉及到用户态和核心态的切换，而在go中，线程是由go自身进行管理的，本身始终处于用户态，因此减少了切换。go将这个线程称为协程，我可能更喜欢叫用户态线程。
2. 并发避不开的是对资源进行加锁开锁，在java中，对一个临界区变量，通过设计同步锁，互斥锁进行，而在go中，为了满足高性能的设计，线程之间通信，引入了管道 chan，通过队列作业而不是竞争作业，相较于java部分线程需要挂起阻塞，go线程始终处于流水线状态。
3. 在空间大小来看，java默认线程将会分配0.5-1mb空间大小，而go可以最小2kb，并且支持动态增加。

在go中管理并发必须要提到的是，GMP模型

- G（Goroutine）用户态的轻量级线程，待调度的任务
- M（Machine）多核cpu数量,内核线程
- p（Processor）带有 G工作队列的控制器，分配单线程作业到具体不同M，做完该任务后再次安排下一个G，属于控制块。（p中若该工作队列空，会去总工作中再次分配，或者去隔壁p取一半给自身，不过我觉得，这个仅仅属于细节，不影响理解）
![](https://imgstroe-redblacktree.oss-accelerate.aliyuncs.com/img/20260319041713633.png)


java线程切换和最小线程分别为**1~10 us**，**1MB**,因为涉及到用户态核心态转变，
而在go中，由于不涉及到用户态核心态切换，时间分别为**0.1~0.5us**，初始栈空间仅约 **2KB**,
那么在一万线程时候，java线程切换所耗时间**5ms ~ 50ms**，占据空间**5GB**，而此时go仅仅需要大约空间**10MB**，时间**0.5ms ~ 2.5ms**
